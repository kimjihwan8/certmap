# 결정 일지

무엇을 정했고, 왜 그렇게 정했는지. 숫자는 실제로 잰 값이다.
블로그·면접에서 "왜 그렇게 했나요?"에 답할 근거로 쓴다.

## 1. "맛집"이 아니라 "검증된 식당"을 보여준다 (2026-10-21)

**결정:** 맛 점수를 매기지 않는다. 공공기관이 공식 지정한 인증(위생·가격·업력)만 보여준다.

**이유:**
- 공공데이터에는 평점·리뷰가 없다. AI로 맛 점수를 만들면 근거 없는 숫자를 지어내는 셈이고, 맞았는지 확인할 방법(정답지)도 없다.
- 네이버·카카오 리뷰 크롤링은 이용약관 위반이다.
- "맛있다"는 주장할 수 없지만 "모범음식점 + 착한가격업소, 인증 2개"는 사실이다.

## 2. 데이터: 인증 6종 + 상가 277만 (2026-10-21 ~ 10-27)

| 데이터 | 건수 (유효) | 받은 곳 |
|---|---|---|
| 모범음식점 | 11,560 | data.go.kr (LOCALDATA는 2026-04-16 폐쇄) |
| 착한가격업소 | 9,709 (음식점만) | data.go.kr 파일 |
| 백년가게 | 1,511 | data.go.kr 파일 |
| 관광공사 맛집 | 13,408 | data.go.kr API |
| 식품안심업소 | 44,977 | 식품안전나라 |
| 안심식당 | 744 (대전만) | 농림축산식품부 (전국은 파일이 너무 커서 못 받음) |
| 상가(상권)정보 | 2,772,484 | 소상공인시장진흥공단 |

**왜 상가 데이터가 필요한가:** 인증 데이터에는 좌표와 정리된 업종이 없고, 기관끼리 공통으로 쓰는 가게 번호도 없다. 상가 데이터에는 전국 가게가 거의 다 있고, 가게마다 고유번호(상가업소번호), 좌표, 업종 소분류가 있다.

**코드 전에 먼저 잰 것:** 착한가격업소를 상가와 상호명 완전일치로 매칭하면 74.3%, 모범음식점은 67.3%였다. 매칭이 너무 쉬우면(80% 이상) 기술적으로 보여줄 게 없어서, 숫자를 보기 전에 기준을 정해두고 쟀다. 결과는 기준선 근처라 매칭 자체보다 매칭 품질 측정에 무게를 두기로 했다.

## 3. 합치는 구조: 각 인증을 상가에 붙인다 (2026-11-06)

**결정:**
```
1단계: 모든 인증 → 상가 매칭 → 상가업소번호를 붙인다
2단계: 상가에서 못 찾은 인증만 다른 인증과 비교한다
       - 상가에 붙은 다른 인증과 같은 가게면 그 상가업소번호를 물려받는다
       - 상가에 없는 인증끼리 같은 가게면 새 번호를 만든다
결과:  같은 상가업소번호를 가진 인증끼리 = 같은 가게
```

**검토한 다른 방법:** 인증끼리 먼저 다 합친 뒤 상가에 붙이기 (참고 레포 방식)

**그 방법을 고르지 않은 이유:**
- 인증 6종을 서로 비교하면 짝이 15개다. 공통 번호가 없어 결국 이름·주소로 비교해야 하니 같은 어려운 문제를 15번 푸는 셈이다. 상가에 붙이는 방식은 "인증 → 상가" 한 가지 문제만 풀면 된다.
- A=B, B=C면 A=C로 묶여서 잘못 묶인 게 연쇄로 번진다. 참고 레포가 스스로 밝힌 한계("같은 건물의 다른 식당이 한 가게로 묶인다")가 이것이다. 상가에 붙이는 방식은 인증 하나가 상가 가게 딱 하나에만 붙어서, 틀려도 번지지 않는다.
- 정답지를 만들기 쉽다. "이 인증과 이 상가가 같은 가게인가?" 쌍에 O/X만 표시하면 된다.
- 소스 하나가 갱신돼도 그 소스만 다시 붙이면 된다.

핵심은 **상가업소번호가 모든 가게의 공통 번호 역할을 한다**는 점이다.

## 4. 같은 가게를 무엇으로 판단하나 (2026-11-06)

**결정:** 지역으로 범위 좁히기 → 같은 건물인지 → 이름 → 업종으로 판가름

| 순서 | 쓰는 정보 | 이유 |
|---|---|---|
| ① | 시도·시군구 | 277만 개 전부와 비교하면 느리고, 다른 동네의 같은 이름(김밥천국)과 헷갈린다 |
| ② | 건물 (도로명 + 건물번호) | 7개 소스 모두에 있는 정보는 이름과 주소뿐이다 |
| ③ | 이름 | 같은 건물에 식당이 여럿일 수 있다 |
| ④ | 업종 | `한우촌`(식당) ↔ `한우촌판매장`(정육점)처럼 이름이 비슷한 다른 가게를 가린다 |

**전화번호는 인증 → 상가 매칭에 못 쓴다.** 상가에 전화번호 열이 없다. 실제로 값이 채워진 소스도 모범음식점(86%)·안심식당(99%)뿐이다. 백년가게·관광공사·식품안심업소는 전화번호 열이 있지만 0%다.

**인증끼리 확실한 열쇠:**
- 모범음식점 `인허가번호` ↔ 식품안심업소 `LCNS_NO`: 같은 번호 체계. 공통 717건 중 716건이 건물 키도 같았다.
- 모범음식점 `전화번호` ↔ 안심식당 `전화번호`

## 5. "주소가 같다" = 같은 건물 (2026-11-06)

**결정:** 도로명 + 건물번호까지만 비교한다. 층·호수·괄호 속 동 이름은 버린다.

**이유:**
- 주소 전체 문자열은 `동일로 1353 (상계동) 지하 1층` vs `동일로 1353`처럼 군더더기 때문에 같은 건물인데도 거의 안 맞는다.
- 층까지 비교하지 않는 이유: 상가의 층정보가 55%만 채워져 있고, 인증 쪽은 층을 적은 곳도 있고 안 적은 곳도 있다.
- 같은 건물 안의 다른 가게는 이름 비교(4번의 ③)로 가린다.

**건물 키 모양:** `시도|도로명|본번-부번` (예: `서울특별시|동일로|1353-0`)

**시군구를 키에서 뺀 이유:** 인천은 2026년에 구가 개편돼 소스마다 이름이 다르다(옛 `중구` vs 새 `제물포구`). 시군구는 매칭할 때 따로 비교한다.

**도로명주소가 없을 때:** 지번주소로 같은 모양의 키(`시도|법정동|번지`)를 만든다. 모범음식점은 도로명주소가 24% 비어 있다.

|---|---|---|

| 착한가격업소 | 음식점 업종 6종 | 12,935 → 9,709 |

## 7. AI는 애매한 쌍의 판정에만 쓴다 (2026-10-22 ~ 11-06)

**결정:** 전처리(주소·이름·지역 정리)는 규칙으로 한다. AI는 "같은 건물 후보 중 어느 것이 같은 가게인가"를 판정하는 곳에만 쓴다.

**전처리에 AI를 안 쓰는 이유:**
- `서울` → `서울특별시`처럼 정답이 하나뿐인 변환은 규칙이 100% 맞고, AI는 가끔 틀린다.
- 277만 행을 AI에 물으면 시간과 비용이 크다. 규칙은 30초면 끝난다.
- 같은 원본을 넣으면 항상 같은 결과가 나와야 비교 실험이 된다.

**AI를 안 쓰기로 한 곳:**
- 맛 점수 (1번 참고)
- 메뉴 분류: 모범음식점 `주된음식종류`는 이미 공공데이터에 있다. 검색은 원문을 색인하면 되고, 카테고리 필터는 상가 소분류를 쓰면 된다.

**AI를 단계별로 적용하고 같은 정답지로 비교한다:**

| 단계 | 방법 |
|---|---|
| 0 | 규칙 (완전일치 → 참고 레포 규칙) |
| 1 | 머신러닝 (이름 유사도·지점명·업종 일치 같은 특징 → 같은 가게일 확률) |
| 2 | 임베딩 (이름의 의미 유사도, 주소가 달라 놓친 후보 찾기) |
| 3 | LLM (애매한 쌍만 판정) |

**미리 정해둔 기준:** 규칙으로 처리한 뒤 남는 "같은 가게인데 AI가 필요한 쌍"이 전체의 5% 미만이면, 서비스에는 AI 매칭을 넣지 않는다. 단, 공부 목적의 비교 실험은 결과와 상관없이 진행한다. 서비스에는 정밀도 98% 이상을 만족하는 가장 단순한 방법을 넣는다.

**지금까지 잰 출발점 (모범음식점 → 상가, 같은 건물 안에서):**

| 방법 | 매칭률 |
|---|---|
| 상호명 완전일치 | 63.9% |
| 공백·괄호 제거 | 77.3% |
| 참고 레포 규칙 | 83.5% |

매칭률은 "짝을 찾은 비율"이지 "맞게 찾은 비율"이 아니다. 정답지를 만들어 정밀도도 함께 재야 한다.

## 9. 자연어 검색: LLM은 질문을 조건으로 바꾸기만 한다 (2026-11-16)

**결정:** "대전역 근처 싼 노포" 같은 질문을 받으면 LLM은 `{위치: 대전역, 조건: [저렴, 오래됨]}`처럼 조건으로 번역만 한다. 가게는 우리 데이터에서 찾는다.

| 표현 | 쓰는 데이터 |
|---|---|
| 싼, 저렴, 가성비 | 착한가격업소 |
| 노포, 오래된, 전통 | 백년가게, 인허가 연도 |
| 깨끗한, 위생 | 식품안심업소, 안심식당, 모범음식점 |
| 맛집 | LX 공사맛집 (직원 추천) |
| 메뉴 이름 | 주된음식종류 원문, 상가 업종 소분류 |

**이유:**
- LLM에게 가게를 직접 물으면 없는 가게를 지어낼 수 있다. 번역만 맡기면 결과는 항상 실제 데이터에서 나온다.
- 위치 좌표도 LLM에게 묻지 않는다. 역 좌표 공공데이터나 지도 API처럼 정답이 있는 곳에서 가져온다.
- 단어 사전 규칙과 LLM을 질문 정답지로 비교한다(7번과 같은 방식).

**조건을 다 만족하는 곳만 보여주지 않는다:** 착한가격업소이면서 백년가게인 곳은 전국 약 40곳, 대전 3곳뿐이다(이름·건물 완전일치로 센 대략값). 조건을 모두 만족하는 곳만 보여주면 결과가 대부분 비므로, 조건을 많이 만족하는 순으로 정렬한다.

**이 기능 때문에 매칭이 더 중요해진다:** "착한가격 + 백년가게"를 찾으려면 두 인증이 같은 가게라는 걸 알아야 한다.

## 10. "맛집" 기준: LX 추천 먼저, 그다음 인증 개수 (2026-11-16) — ⚠️ 32번에서 LX 우선을 뺐다

**결정:** 정렬 순서는 ① LX 공사맛집 추천 여부 ② 인증·추천 목록에 실린 개수 ③ 거리.

**다른 서비스 조사:**
- 구글 지도: 관련성 + 거리 + 유명도. 유명도에는 리뷰뿐 아니라 "웹의 기사·목록에 실린 것"도 들어간다 (공식 도움말).
- 네이버 플레이스: 검색어 유사도·인기도·거리·정보 충실성 (공식 원문은 못 찾았고 2차 자료).
- 미쉐린 빕구르망·블루리본: "누가 골랐나"가 기준 (평가원·독자).

**LX 공사맛집을 쓰는 이유:** 6종은 모두 위생·가격·업력 인증이다. 맛 때문에 사람이 고른 공공데이터는 이것뿐이다. 우리가 맛 점수를 만드는 게 아니라 "공공기관 직원이 추천했다"는 사실을 보여주므로 1번 결정과 부딪히지 않는다. 화면에는 "맛집 인증"이 아니라 "LX 직원 추천"으로 출처 그대로 적는다.

**인증 개수를 유명도 대신 쓰는 이유:** 리뷰가 없으니 구글의 "목록에 실린 것"에 해당하는 신호만 쓸 수 있다.

**LX 데이터의 한계:**
- 2,013곳(대전 41곳)뿐이다.
- 제안수 열이 사실상 비어 있어(2곳만 값 있음) 추천 강도는 알 수 없고, 목록에 있느냐 없느냐만 쓴다.
- 이름·건물 완전일치로 대략 세면 33%가 이미 인증 데이터에 있고(관광공사 26%, 모범음식점 10.5%), 88.6%는 상가에 같은 건물이 있다.

**순위에는 정답 순서가 없다:** 매칭처럼 정밀도로 증명할 수 없다. 그래서 정렬 기준을 화면에 그대로 보여준다.

## 11. 위치는 우리 데이터에서 찾는다 (2026-11-16)

**결정:** LLM은 문장에서 장소 이름("대전역")만 뽑는다. 좌표는 상가 데이터에서 찾는다.

| 표현 | 찾는 곳 |
|---|---|
| 대전역, 서대전역 | 상가 건물명이 **정확히 같은** 가게들의 평균 좌표 (대전역 11곳 → 36.33442, 127.43210) |
| 은행동 | 주소의 동 이름 |
| 성심당 근처 | 상가 상호명 |
| 한밭수목원처럼 가게가 없는 곳 | 지도 API (카카오 로컬 등) |

**정확히 같은 이름만 쓰는 이유:** "대전역"이 들어간 건물명으로 찾으면 `서대전역코아루써밋`, `대전역대라수어썸브릿지2단지` 같은 아파트가 섞인다.

## 12. DB 모양: 가게 표 + 인증 표, 체크 컬럼은 계산해서 채운다 (2026-11-16)

**결정:**
```
stores (가게 1곳 = 1행)               certs (인증 1건 = 1행)
store_id (상가업소번호)  ◀──────────  store_id
상호명, 좌표, 업종                     source, 지정일, 메뉴·가격, 인허가 연도, 유효기간
모범 / 착한가격 / 백년 … (true/false)
cert_count
```

**이유:**
- 체크 컬럼이 있으면 "싼 노포"가 `착한가격 AND 백년가게` 한 줄로 끝난다 (사용자 제안).
- 체크만 남기면 지정일·메뉴·인허가 연도처럼 상세 화면과 "노포" 판단에 필요한 정보가 사라진다. 그래서 인증 표를 따로 둔다.
- 체크 컬럼과 `cert_count`는 인증 표에서 계산해 채운다. 손으로 따로 관리하면 두 표가 어긋날 수 있다.

**이 표는 매칭을 대신하지 않는다.** 체크를 넣으려면 "모범음식점 목록의 고려회관 = 상가 1234번"을 먼저 알아야 하고, 그게 매칭이다.

**식당만 고르는 건 매칭 뒤에 한다:** 상가 업종이 틀린 가게가 있어서, 먼저 거르면 인증받은 식당이 사라진다(6번 참고). 저장 대상은 "인증이 붙은 가게 + 상가 업종이 음식인 가게"다.

**상가에 없는 인증 가게도 행으로 넣는다:** 3번의 2단계처럼 새 번호를 만든다. 그렇지 않으면 인증 가게의 3~14%가 지도에서 사라진다.

## 13. 규칙 판정 v0: 이름이 비슷하면 음식 업종일 때만 확정 (2026-11-24)

**먼저 잰 것** (`scripts/measure_candidates.py` → `results/candidates_profile.txt`):

같은 건물 후보 중 이름이 가장 잘 맞는 수준 ('건물을 찾은 인증' 중 비율)

| 소스 | 건물 못 찾음 | 같은 이름 | 포함 | 비슷함 | 맞는 이름 없음 |
|---|---|---|---|---|---|
| 모범음식점 | 2.8% | 82.0% | 5.3% | 2.0% | 10.8% |
| 착한가격업소 | 4.1% | 80.3% | 5.4% | 2.7% | 11.6% |
| 백년가게 | 11.2% | 84.3% | 2.6% | 1.1% | 11.9% |
| 관광공사 | 6.7% | 67.2% | 16.4% | 3.8% | 12.5% |
| 식품안심업소 | 2.5% | 62.3% | 9.3% | 7.6% | 20.9% |
| 안심식당 | 3.5% | 67.3% | 6.8% | 3.6% | 22.3% |

- 같은 이름 = 정규화한 이름, 상호명+지점명, 지점명 뗀 본이름 중 하나가 같다
- 포함 = 한쪽 이름이 다른 쪽을 포함 (`청진옥` ⊃ `청진`)
- 비슷함 = 글자 2개 묶음 유사도 0.5 이상 (`미도리회집` ≈ `미도리횟집`)

**결정:**
```
① 같은 이름 후보 1곳                         → 확정
② 같은 이름 후보 여럿 → 음식 업종이 1곳이면    → 확정, 아니면 보류
③ 포함·비슷함 후보 중 음식 업종이 1곳이면      → 확정, 아니면 보류   ← 사용자 선택
④ 맞는 이름 없음 / 같은 건물 후보 없음         → 상가에 없음 (3번의 2단계로)
```

**③을 이렇게 정한 이유:** 포함·비슷함 구간에는 같은 가게(`청진옥` → `청진`)와 다른 가게(`조선호텔앤리조트 스시조` → 호텔, `남도미항 용산아이파크몰점` → `용산아이파크헤지스` 의류)가 섞여 있다. 업종 조건 하나로 비식당 오답을 걸러낸다. 이 규칙이 AI 단계들이 이겨야 할 기준선이다.

**검토한 다른 방법:** ③을 전부 보류(정밀도는 높고 매칭률은 낮음), 전부 확정(참고 레포와 비슷, 오답 많음)

**시군구 필터:** 건물 키에 시군구가 없어서(5번) 같은 도의 같은 도로명(여러 도시의 `중앙로`)이 섞일 수 있다. 인증의 시군구를 상가와 맞춘 경우에만 시군구가 다른 후보를 뺀다. 빠진 건 0.1~0.4%p로 드물었다.

**v0 결과 (확정 비율):** 모범 84.9%, 착한가격 83.6%, 관광공사 78.9%, 백년 76.0%, 안심 72.8%, 식품안심 70.9%. 참고 레포 규칙(모범 83.5%)과 매칭률은 비슷하다. **이게 맞게 붙었는지(정밀도)는 정답지로 잰다.**

## 14. 정답지: 어려운 구간을 더 많이 뽑는다 (2026-11-24)

**결정:** 인증 300건. 한 건 = 인증 1개 + 같은 건물 후보 최대 9곳. 라벨은 "같은 가게인 후보 번호 / 후보 중에 없음 / 모르겠음".

| 구간 | 전체 크기 | 뽑은 수 |
|---|---|---|
| 같은 이름 후보 1곳 | 53,121 | 60 |
| 같은 이름 동점 | 933 | 40 |
| 포함 | 7,304 | 70 |
| 비슷함 | 4,320 | 70 |
| 맞는 이름 없음 | 13,323 | 60 |

**이유:**
- 무작위로 300건을 뽑으면 70%가 쉬운 "같은 이름"이라 애매한 구간이 수십 건뿐이다. AI가 필요한 곳은 애매한 구간이다.
- 구간마다 뽑는 비율이 다르므로, 전체 정밀도는 구간별 결과에 전체 크기를 곱해 합친다(층화 추출). 그래서 구간 크기를 `test_strata.json`에 함께 저장했다.
- 쌍마다 O/X를 다는 대신 후보 중 하나를 고르게 했다. 더 빠르고, "후보에 정답이 아예 없다"도 기록된다.

**공정하게 라벨링하려고:**
- 순서를 섞어서 어느 구간인지 안 보이게 했다.
- 규칙이 고른 답을 화면에 보여주지 않는다. 보이면 그 답에 끌려간다.
- 테스트셋은 한 번 뽑으면 고정한다(시드 20261124, 덮어쓰기 막음). 라벨을 단 뒤에 바뀌면 숫자를 비교할 수 없다.
- 이 300건은 **채점에만** 쓴다. 규칙이나 모델을 이 300건을 보며 고치면 시험 문제를 보고 공부한 셈이 된다. ML 학습용 라벨은 따로 만든다.

**한계:**
- 같은 건물 후보가 0곳인 인증(2.5~11%)은 고를 후보가 없어 뽑지 않았다.
- 소스 비율이 실제 비율을 따라가서 식품안심업소가 194건(65%)이고 백년가게 4건, 안심식당 2건이다. 소스별 정밀도는 말하기 어렵다.

**도구:** `python3 scripts/label_server.py` → 브라우저에서 고르면 `data/labels/test_labels.csv`에 바로 저장된다.

## 15. 정답지 라벨은 AI 3명이 독립적으로 달고 다수결로 정했다 (2026-11-24)

**결정:** 사용자 요청으로 Claude(A)와 서브에이전트 2개(B·C)가 서로의 답을 보지 않고 같은 기준서(`docs/labeling-guide.md`)로 300건을 각자 라벨링했다. 최종 답은 다수결이다 (`scripts/merge_labels.py`).

**결과** (`results/label_agreement.txt`):
- 3명 일치 293건, 2:1 7건, 3명 모두 다름 0건
- 두 명씩 일치율 98.3~98.7%, Fleiss 카파 0.973 (가게 고름 / 없음 / 모르겠음 세 범주)
- 최종: 가게 있음 196 / 없음 82 / 모르겠음 22 (채점에서 뺌)

**라벨링 도중 기준서를 고친 것:** 상가에 같은 가게가 두 번 실린 경우(이름·지점 같음)를 "모르겠음"이 아니라 "둘 다 정답(`1|2`)"으로 처리한다. 300건 중 36건이 이 경우였다. B·C에게도 알려 다시 반영했다.

**한계 (블로그에 그대로 쓸 것):**
- 사람이 아니라 AI 3명이 달았다. 셋 다 Claude 계열이라 같은 방향으로 틀릴 수 있다. 일치율이 높다고 정답이라는 뜻은 아니다.
- 나중에 "LLM 판정"(7번의 3단계)을 이 정답지로 채점하면 AI가 AI를 채점하는 셈이 된다. 그 실험 전에 사람이 일부를 확인해야 한다.
- 남은 "모르겠음"은 대부분 휴게소·공항 푸드코트다. 인증은 "OO휴게소 우동 코너"처럼 코너 단위로 받는데, 상가에는 휴게소 운영사가 한 줄로만 있다. 같은 가게로 볼지는 아직 정하지 않았다.

## 18. 시험용 채점: v1을 서비스에 쓰고, AI 매칭은 넣지 않는다 (2026-11-24)

**test 라벨** (새 서브에이전트 3명, `results/label_agreement_test.txt`): 3명 일치 292건, 2:1 8건, 카파 0.963. 최종 가게 있음 201 / 없음 75 / 모르겠음 24.

**test 점수** (`results/score_test.txt`, 한 번만 채점):

| | v0 | v1 |
|---|---|---|
| 정밀도 | 98.9% (95% 98.1~99.5) | **99.7%** (95% 99.4~100.0) |
| 재현율 | 94.0% | **95.6%** |
| 놓친 몫 | 5.0% (5% 이상일 확률 46%) | **3.6%** (95% 2.0~5.4, 5% 이상일 확률 6%) |

**읽는 법:**
- v1의 test 점수(99.7% / 95.6%)가 dev 점수(99.8% / 96.1%)와 거의 같다. dev를 보며 고쳤지만 dev에만 맞춘 규칙이 아니었다는 뜻이다.
- v0는 dev에서 놓친 몫 4.0%였지만 test에서는 5.0%로 기준 경계에 걸렸다. 정답지를 한 벌만 썼다면 이 차이를 몰랐다.
- v1은 비슷함 구간 재현율이 87.8% → 80.5%로 내려갔다. 비슷함을 엄격하게 본 대가다. 대신 동점 구간(7.7% → 89.7%)에서 더 많이 찾아 전체 재현율은 올랐다.
- v1이 틀린 3건 중 2건(천안호두휴게소 던킨, 진주휴게소 한식)은 라벨러끼리도 2:1로 갈린 휴게소 코너다. 정답 자체가 확실하지 않은 곳이다.

**결정:**
- 서비스 매칭은 **v1**을 쓴다. 정밀도 98% 기준을 여유 있게 넘는다.

## 20. DB: PostgreSQL + PostGIS + pgvector (2026-11-26)

**결정:** 매칭 결과를 PostgreSQL에 담고, 위치는 PostGIS, 의미 검색은 pgvector로 한다. 로컬에서는 Docker로 띄운다. (사용자 선택)

**필요한 검색 세 가지** ("대전역 근처 얼큰한 국물 싼 집"):
- 위치: "대전역 근처" → 좌표 반경 안
- 조건: "싼" → `착한가격 = true`
- 의미: "얼큰한 국물" → 업종 "해장국/감자탕", 메뉴 "짬뽕"처럼 단어가 안 겹쳐도 찾아야 한다

**고른 이유:** 세 가지를 SQL 한 쿼리로 묶을 수 있다. 실제 서비스에서 흔한 조합이라 설명하기 쉽다. 벡터 색인(HNSW)이 있어 규모가 커져도 빠르다.

**버린 선택지:**
- SQLite + R*Tree + sqlite-vec: 설치가 없어 편하지만, sqlite-vec는 0.x 초기 버전이고 색인 없이 전부 비교한다. 조건과 의미 검색을 섞기 어렵다.
- 일반 DB + 벡터 DB(Qdrant·Chroma) 따로: 가게 정보를 두 곳에 맞춰 둬야 한다. 이 규모엔 과하다.
- Elasticsearch: 다 들어 있지만 무겁다. 무엇보다 **초성·오타 검색 역색인을 직접 구현**하려던 기술 포인트를 엔진이 대신해 버린다.

**용어:** 이건 RAG라기보다 **하이브리드 검색**이다. RAG는 찾은 결과를 LLM이 받아 답을 문장으로 쓰는 방식이고, 우리는 9번대로 LLM이 질문을 조건으로 바꾸기만 한다.

**규모:** 상가 음식점 840,255곳 + 음식 업종이 아닌 인증 가게 + 상가에 없는 인증 가게 ≈ 86만 행. 벡터를 전부 만들면 384차원 약 1.3GB, 1024차원 약 3.5GB다. 인증 가게만 만들지는 의미 검색 단계에서 정한다.

## 25. 2단계: 상가에 없는 인증은 물려받거나, 건물 안에서만 묶어 새 가게로 (2026-11-26)

**측정 먼저:** 상가에서 못 찾은 인증 20,004건 중 상가에 붙은 인증과 이어지는 것은 100건도 안 됐다. 모범음식점이 상가에 붙으면 같은 인허가번호의 식품안심업소도 이미 같은 가게에 붙어 있었다는 뜻이다. 1단계 매칭이 소스끼리 일관됐다는 증거다.

**규칙** (`scripts/match_stage2.py`):
1. **물려받기:** 상가에 붙은 인증과 아래 중 하나가 같으면 그 가게 번호를 물려받는다. 이어지는 가게가 둘 이상이면 물려받지 않는다 (v1과 같은 정밀도 우선).
   - 인허가번호
   - 전화번호 + 같은 건물 (전화번호만으로는 본사 대표번호가 겹칠 수 있다)
   - 같은 건물 + 같은 이름
2. **묶기:** 남은 인증끼리 같은 기준으로 묶는다. 단, **같은 건물 안에서만**, **다른 소스끼리만** 묶는다.
   - 건물을 넘어 묶으면 A=B, B=C → A=C로 잘못 묶인 게 번진다 (3번에서 걱정한 것).
   - 같은 소스끼리 안 묶는 이유: 같은 목록에 두 번 실린 건 다른 가게(같은 건물 2호점 등)일 수 있다.
3. **새 가게:** 묶음 하나 = 새 가게 하나.
   - 번호: `C-` + 묶음에서 가장 앞선 인증 번호.
   - 이름: 모범음식점 → 백년가게 → 착한가격 → 안심식당 → 식품안심 → 관광공사 → LX 순으로 대표 인증을 고른다.
   - 좌표는 23번 순서로 붙이고 출처를 `coord_source`에 남긴다.

**결과** (`results/match_stage2.txt`):

| | 건수 |
|---|---|
| 물려받음 (이름 43 / 인허가번호 19 / 전화 6) | 68 |
| 물려받기 보류 (가게 2곳 이상과 이어짐) | 4 → 새 가게로 |
| 묶음 536개에 들어간 인증 | 1,218 |
| 새 가게 | 19,254 (좌표: 같은 건물 16,290 / 원본 886 / 지오코딩 대기 2,078) |

**DB 반영:** 이제 모든 인증에 가게 번호가 있다 (`certs.store_id NOT NULL`). 가게 860,695곳, 인증 붙은 가게 78,365곳이다.

**한계:**
- 2단계 묶음의 정확도는 재지 않았다. 열쇠가 모두 같은 건물 안이거나 인허가번호라 틀릴 여지는 작지만, 측정한 숫자는 아니다.

## 27. 지도: 인증 가게만, MapLibre + PostGIS 벡터 타일, 서버는 Hono (2026-11-26)

**결정 (사용자 선택, 네 가지 모두):**

| | 고른 것 | 이유 |
|---|---|---|
| 기본 지도에 찍는 것 | 인증·추천 붙은 가게 78,365곳 | 서비스가 "검증된 식당"이다. 나머지 84만 곳은 검색 결과로만 보여준다 |
| 지도 | MapLibre GL (오픈소스, WebGL) | GPU로 그려 점 수십만 개도 부드럽다. 우리 벡터 타일을 그대로 얹는다. 키·비용이 없다 |
| 점 그리기 | 벡터 타일 (PostGIS `ST_AsMVT`) | 86만 곳까지 늘려도 된다. 타일 단위로 캐시할 수 있다. 처음 계획한 "대량 점 렌더링" 기술 포인트다 |
| 서버 | Hono | 서버 라우트의 타입을 화면이 그대로 쓰는 RPC가 있다. TS로 통일한 이유(21번)를 직접 살린다 |

**버린 선택지:**
- 카카오·네이버 지도: 한국 지도 품질은 가장 좋다. 하지만 마커가 HTML 요소라 수만 개면 느리고, 벡터 타일을 얹기 어렵다.
- 브라우저 클러스터링(supercluster): 7.8만 곳은 되지만 86만 곳은 데이터가 너무 크다.
- 서버 클러스터링: 지도를 움직일 때마다 쿼리하고, 캐시하기 어렵다.

**대가:** 바탕 지도가 OSM 기반이라 한국 상호·건물 표시가 카카오보다 빈약하다. 가게 점은 우리가 그리므로 큰 문제는 아니다. 브이월드 바탕 지도로 바꿀 수 있다.

**확대 수준별로 다르게 준다:** 낮은 확대(전국·도 단위)에서는 타일 하나에 점이 수만 개라 타일이 무거워진다. 낮은 확대에서는 타일을 격자로 나눠 칸마다 점 하나와 개수만 주고, 높은 확대에서는 가게 하나하나를 준다.

**측정으로 정한 값** (`results/tiles.txt`):
- z7 타일에 가게를 하나하나 넣으면 점 28,863개, **2.6MB**. 격자로 묶으면 **1.3KB**다.
- z12도 하나하나는 103KB라 무겁다. 그래서 경계를 **z12까지 격자, z13부터 하나하나**로 한 칸 올렸다.
- 격자는 처음 32×32(칸 16px)였다. 원 지름(최대 48px)보다 칸이 작아서 z8 화면에 원 1,510개가 겹쳐 읽을 수 없었다. 8×8(칸 64px)로 바꾸니 266개로 줄고 겹치지 않았다.
- 격자 원점을 세계 끝에 맞춰서, 칸 경계가 타일 경계와 딱 맞는다. 한 칸이 두 타일에 걸쳐 두 번 세지지 않는다.

**구현:**
- 서버 `apps/server` (Hono, 8790번 포트): `GET /api/tiles/:z/:x/:y`(MVT), `GET /api/stores/:id`(가게 상세 + 인증 목록).
- 화면 `apps/web` (React + Vite + MapLibre v6): 지도, 범례, 가게 상세 패널. 화면은 서버의 `AppType`을 가져다 써서 응답 타입을 공유한다.
- DB에 타일용 웹 메르카토르 좌표 열(`geom_3857`)과 인증 가게만 담은 부분 색인을 추가했다.

**만들며 겪은 것:**
- MapLibre v6는 웹 워커 파일을 자기 파일 옆에서 찾는다. Vite가 개발 중에 라이브러리를 미리 묶어 다른 폴더로 옮기면 워커를 못 찾는다("Worker failed to load"). `optimizeDeps.exclude`로 해결했다. 배포 빌드에서도 되는지는 배포 단계에서 확인한다.
- 가게 상세의 날짜는 SQL에서 글자로 바꿔 보낸다. pg가 date를 자바스크립트 Date로 바꾸면 시간대 때문에 하루가 밀릴 수 있다.

## 28. 검색 1차: 상호 자동완성은 가볍게 (pg_trgm + 가까운 순) (2026-11-26)

**검색창 구조 (사용자 동의):** 검색창 하나. 치는 동안에는 상호 자동완성, 엔터를 치면 자연어 검색. 순서는 ① 상호 검색 → ② 조건 칩 + 장소 → ③ 자연어 → 칩 (규칙 먼저, 사용자가 쓴 질문 정답지로 채점) → ④ 의미 검색 (관광공사 소개글 수집이 끝난 뒤).

**상호 검색 범위:** 86만 곳 전부 (사용자 선택). 인증 없는 가게도 찾아지고 "공공 인증 없음"으로 보여준다. "우리 동네 그 집, 인증 있나?"에 대한 답이 된다.

**pg_trgm을 86만 개 이름으로 재본 결과:**

| | 결과 |
|---|---|
| 세 글자 이상 (`성심당`) | 색인 없이 57ms → 색인 0.24ms |
| 두 글자 (`심당`) | 색인이 있어도 31ms. trigram은 3글자 묶음이라 두 글자로는 색인을 못 쓴다 |
| 짧은 이름 오타 (`성싱당`) | 못 찾음 (유사도 0.14) |
| 긴 이름 오타 (`신당동떡볶기`) | 찾음 (0.56) |
| 초성 (`ㅅㅅㄷ`) | 못 찾음 |

trigram은 영어용이다. 한국어는 한 글자가 음절 하나라, 영어 trigram에 해당하는 건 한국어 두 글자 묶음이다.

**결정 (사용자):** 검색 엔진 서비스가 아니므로 1차는 가볍게 간다. pg_trgm 색인에 위치 색인의 "가까운 순으로 꺼내기"(`ORDER BY geom <-> 중심 LIMIT n`)를 더한다. 초성·짧은 이름 오타는 나중에 개선한다.

**가까운 순으로 몇 개만 보여주면 두 글자도 빠르다:**

| 검색 | 시간 |
|---|---|
| `국밥`, 전국에서 대전역 가까운 순 5개 | 0.8ms |
| `당` (5만 4천 곳이 걸림) | 0.6ms |
| `훠궈` (드묾) | 5ms |
| `랍스`, 제주 기준 (드묾) | 751ms ← 최악 |

위치 색인이 가까운 곳부터 꺼내 이름을 확인하다가 n개가 차면 멈춘다. 흔한 단어일수록 빨리 끝난다. 드문 단어는 멀리까지 훑어서 느리다. 1차는 쿼리 시간 제한으로 막는다.

**구현:**
- 서버 `GET /api/search?q=&lat=&lon=` (`apps/server/src/search.ts`): 가까운 순 8개. 쿼리 시간 제한은 300ms이고, 넘으면 빈 결과를 준다. 좌표 없는 가게(지오코딩 대기)는 뺀다.
- DB `stores.search_text`: 상호 + 지점명을 소문자로, 띄어쓰기 없이 만든 열이다. pg_trgm 색인을 건다. 그래서 `성심당 본점`처럼 띄어 써도 찾는다. LIKE 특수문자(`%`, `_`)는 글자 그대로 찾는다.
- 화면 `SearchBox.tsx`:
  - 치기를 멈추고 200ms 뒤에 한 번만 묻는다. `성심당`을 치는 동안 요청은 1번이다.
  - 늦게 온 옛 응답은 버린다.
  - ↑↓·Enter·Esc로 고른다.
  - 결과마다 공공 인증 / LX 추천 / "공공 인증 없음" 표시를 단다.
- 결과를 고르면 지도가 그 가게로 이동하고 빨간 표시를 띄운다. 인증 없는 가게는 타일에 점이 없어서 이 표시가 필요하다. 상세 패널에는 "공공 인증·추천 목록에 실리지 않은 가게예요"라고 적는다.

**나중에 개선할 때의 기준선:** 위 표가 그대로 기준선이다. 두 글자·초성·자모 역색인을 직접 만들면 드문 단어 751ms, 오타·초성 "못 찾음"이 얼마나 바뀌는지로 잰다.

## 30. 검색 2차: 조건 칩 + 장소 (2026-11-26)

**칩:** 착한가격, 백년가게, 모범음식점, 위생(식품안심업소 또는 안심식당), LX 추천, 관광정보, 업종(상가 소분류, 인증 음식점 기준 42종).

- 응답 시간은 5~60ms다.

**만들며 고친 것:**
- 장소를 고른 뒤 지도가 도착(moveend)할 때까지 기준점이 안 바뀌었다. 그사이 대전 결과가 "서울역 근처" 머리말 아래 보였다. 이제 고르는 즉시 기준점을 바꾼다.
- 사용자가 지도를 직접 끌면 "○○ 근처" 표시를 지운다.
- 상세·건물 목록을 보는 동안에는 지도가 움직여도 다시 찾지 않는다. 돌아왔을 때 순서가 바뀌어 있으면 헷갈린다.
- 업종을 안 골랐을 때 SQL에 안 쓰는 매개변수를 넘겨서 Postgres가 거절했다. 쓰는 매개변수에만 번호를 매기도록 고쳤다.

**한계:**
- 정렬에서 실린 목록 수가 거리보다 앞이라, 범위가 넓어지면 먼 가게가 가까운 가게보다 위에 올 수 있다 (예: LX 추천만 고르면 3.5km 가게가 990m 가게보다 위).
- 장소는 상가 건물 이름에 있는 곳만 찾는다. "한밭수목원"처럼 가게가 없는 곳은 지도 API가 필요하다 (11번).

## 31. 검색 3차: 자연어 → 칩, 규칙 v0 (2026-11-26)

**계기:** 사용자가 검색창에 "대전역 근처 싼 노포"를 쳤는데 "찾지 못했어요"가 떴다. 이름 검색만 있어서 "대전역근처싼노포"라는 가게를 찾은 것이다.

**구조:** 치는 동안에는 이름 검색, 엔터를 치면 자연어 해석이다 (28번). 방향키로 목록을 골랐을 때만 엔터가 가게 열기다.
- 해석기(`apps/server/src/parse.ts`, `GET /api/parse`)는 칩을 채우기만 한다. 가게는 언제나 DB에서 나온다 (9번).
- 해석 결과는 검색창 아래에 "싼 → 착한가격", "반영 못 함: 분위기"처럼 그대로 보여준다.

**규칙 v0:**
1. 반대 뜻 걸러내기: `비싼`은 `싼`을 품지만 착한가격이 아니다 → 반영 못 함.
2. 사전: 단어 안에 사전 낱말이 들어 있으면 그 칩이다.
   - 인증 (9번 표): 싼·저렴·가성비·착한 → 착한가격 / 노포·오래된·전통 → 백년가게 / 깨끗·위생 → 위생 / 맛집 → LX 추천
   - 업종: 국밥·짬뽕·칼국수 등 약 60개 낱말 → 상가 소분류
3. 장소: "근처·주변·앞"과 조사를 뗀 단어가 상가 건물 이름과 정확히 같으면 장소다 (11번).
4. 군말("집", "식당", "좋은")은 버린다.
5. 나머지는 "반영 못 함"으로 보여준다.

**시험** (서버에서 해석만):

| 질문 | 장소 | 칩 | 반영 못 함 |
|---|---|---|---|
| 대전역 근처 싼 노포 | 대전역 | 착한가격, 백년가게 | |
| 서대전역 근처 맛집 | 서대전역 | LX 추천 | |
| 서울역 앞 깨끗한 짬뽕 | 서울역 | 위생, 중국집 | |
| 비싼 한우 | | 소고기 | 비싼 |
| 분위기 좋은 국밥집 | | 국/탕/찌개류 | 분위기 |

화면에서도 확인했다: "대전역 근처 싼 노포"에 엔터를 치면 칩 두 개가 켜지고, 대전역 기준으로 "조건 2개 모두 1곳(시쥬) · 일부 29곳"이 나온다.

**아직 안 한 것 (채점):** 이 규칙이 얼마나 맞는지는 아직 모른다. 사용자가 쓴 질문 정답지(50~100개)로 채점해야 한다. AI가 만든 정답지로 채점하면 의미가 약하다 (15번에 적은 한계). 채점 뒤 규칙이 못 푸는 몫이 크면 LLM(Claude·Jev)과 비교한다.

**알려진 약점:**
- 단어 안에 낱말이 "들어 있으면" 칩으로 읽는다. 그래서 `회사`, `회식` 같은 말을 따로 막아 둬야 한다. 정답지로 채점하면 이런 오탐이 더 나올 것이다.
- "분위기 좋은"처럼 두 단어로 된 표현은 "분위기"만 반영 못 함에 뜨고 "좋은"은 군말로 버려진다.
- "회식하기 좋은", "분위기"는 관광공사 소개글 의미 검색(4단계, 24번)으로 반영할 후보다.

## 32. "맛집" = LX가 아니다. 정렬에서 LX 우선을 뺀다. 화면 다듬기 (2026-11-26)

**사용자 지적:** "맛집이라 치면 무조건 LX가 뜨는데 이렇게 하지마. 이렇게 하면 LX 추천만 맛집인거잖아."

**10번을 고친다:**
- "맛집", "유명", "인기", "추천", "맛있는"은 칩을 켜지 않는다. **"여러 공공 목록에 실린 가게일수록 위"** 로 읽는다. 원래 정렬이 그렇기 때문에 칩이 필요 없다.
- LX 칩은 "LX 추천"처럼 콕 집어 말할 때만 켠다.
- 정렬에서 LX 우선을 뺀다. **만족한 조건 수 → 실린 목록 수 → 거리**. LX는 7개 목록 중 하나로 센다.
- 타일의 대표 가게, 건물 목록 순서도 같은 기준으로 바꿨다.
- 지도 점 색: "LX면 주황"을 없애고 **실린 목록 수(1 / 2 / 3개 이상)** 로 진하기를 나눈다.

**화면 다듬기 (사용자: "UX가 너무 별로, UI도 별로"):**

| 문제 | 바꾼 것 |
|---|---|
| 처음 사이드바가 안내 글뿐 | 처음부터 "이 근처 인증 가게"(실린 목록 많은 순)가 뜬다. 칩 없는 `/api/find`가 이걸 준다 |
| 사이드바는 어둡고 지도는 밝아 따로 놂 | 다크 모드면 바탕 지도도 OpenFreeMap `dark`로 바꾼다 |
| 칩 두 줄 + 해석 상자 + 머리말 + 정렬 설명이 쌓여 목록이 밀림 | 칩은 한 줄 가로 스크롤, 해석은 한 줄, 머리말은 제목 + 작은 설명 한 줄 |
| ✓/✗ 취소선 배지가 지저분함 | 가게마다 실린 목록을 출처별 색 배지로 보여준다. 칩을 골랐으면 맞는 배지만 진하게, 나머지는 흐리게. 조건이 2개 이상이면 오른쪽에 "2/2" |
| 목록과 지도가 따로 놂 | 목록에 마우스를 올리면 지도에서 그 가게에 고리가 생긴다 |
| 상세가 밋밋함 | 출처별 색 카드, 주소 복사, 네이버·카카오 지도에서 보기 링크(리뷰는 거기서. 크롤링은 하지 않는다) |
| 기준점이 지도 중심뿐 | 내 위치 버튼 |
| 검색 결과 이름표가 기존 이름표와 겹침 | 인증 가게는 원래 이름표만 쓰고, 인증 없는 결과에만 따로 이름을 단다 |
| 처음부터 첫 줄이 선택된 것처럼 칠해짐 | 방향키로 골랐을 때만 칠한다 |
| 휴대폰에서 칩 줄이 화면을 가로로 넓힘 | 그리드 칸에 `minmax(0, 1fr)`와 `min-width: 0` |

**확인:** 밝은 모드·어두운 모드·휴대폰(390px) 스크린샷을 봤다. "대전역 맛집"은 이제 칩 없이 📍대전역 + "실린 목록 많은 순"으로 읽고, 태화장(4개)·한밭식당(3개) 순으로 나온다.
